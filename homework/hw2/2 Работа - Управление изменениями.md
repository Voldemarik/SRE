## 📋 Контекст

В первой работе ты создал HTTP-приложение и развернул его в Kubernetes. Теперь команда хочет включать новое поведение постепенно и выключать его без сборки нового образа и перезапуска Pod 🔄

## 💬 Запрос заказчика

*«Добавьте новый формат приветствия. Сначала он должен быть выключен. Дежурный должен уметь включить и выключить его во время работы сервиса, а мы — проверить, что переключение не требует нового релиза.»*

---

## 📚 Постановка задания

Добавь в приложение runtime feature flag `new-greeting`.

- `GET /message` возвращает старый текст, пока флаг выключен, и новый текст, когда он включен.
- `GET /admin/feature?enabled=true` включает флаг; `GET /admin/feature?enabled=false` выключает его.
- После переключения следующий запрос к `/message` должен показать новое состояние без перезапуска процесса или Pod.

Сделай изменение на основе приложения из первой работы. В CI автоматически проверь оба состояния. Затем выкатай образ в свой локальный Kubernetes и продемонстрируй переключение флага, сохраняя тот же Pod. Административный endpoint предназначен только для локального учебного кластера и не должен выставляться в интернет.

---

## ⚠️ Требования к работе

- Реализуй `/message` и `/admin/feature` с поведением, описанным выше; по умолчанию флаг выключен.
- Добавь автоматические тесты: начальное состояние выключено, включение меняет ответ, выключение возвращает старое поведение.
- Создай GitHub Actions workflow в `.github/workflows/ci.yml`: на push и pull request он запускает тесты и собирает Docker-образ.
- После выкладки проверь переключение флага через HTTP-запросы. Зафиксируй идентификатор Pod до и после переключений, чтобы подтвердить отсутствие перезапуска.
- В отчете `homework/hw2/readme.md` укажи команды, результаты CI, ответы endpoint до/после переключения и вывод: чем feature flag отличается от выкладки новой версии.

### Как использовать пример с лекции

На лекции будет показан [пример CI](https://github.com/dakmaev1440/sre-lecture-05-ci-demo). Его можно форкнуть как основу для структуры репозитория и workflow. Для домашней работы нужно изменить само приложение и проверки: тестировать runtime-переключение `new-greeting`, а не повторять `/version` и HTTP smoke test из демонстрации.

В CI не нужны Kubernetes-кластер, self-hosted runner или публикация образа в registry. GitHub Actions запускает unit-тесты и собирает образ на временном runner. Проверка переключения в Kubernetes выполняется отдельно локально.
